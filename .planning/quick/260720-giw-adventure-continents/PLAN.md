# Quick Task 260720-giw — 모험의 서 대륙별 분류

## 요구

모험의 서는 대륙마다 달성도를 채우는 수집품 묶음이다. 지금 `/adventure`는 이름 검색만 가능해서
"루테란 서부를 채우려면 뭐가 얼마인지"를 볼 수 없다. 대시보드 물품 카테고리처럼 **좌측에 `대륙`
상위 카테고리(지도 아이콘) + 하위에 각 대륙**을 두고, 고르면 그 대륙의 수집품 시세만 보여준다.

## 데이터 — 매핑은 API가 안 준다

`/markets/options` 실측: 카테고리 `100000 모험의 서`는 **Subs가 빈 배열**이고 대륙 필터 파라미터도
없다. 아이템 이름에도 대륙 표시가 없다. 웹 조사도 전부 실패했다(공식 게임가이드·공식 공략글·
나무위키 403·인벤·INTY — 대륙별 거래 가능 수집품 목록을 가진 곳이 없음).

→ **사용자가 인게임 모험의 서를 직접 보며 정리한 노션 문서**가 유일한 출처다.

### 검증 완료 (추측 0행)

노션 20대륙 × 7개 = 140개를, 거래소 카테고리 100000의 전량(14페이지)과 대조했다:

- 개수: 140 == 140 (거래소 `TotalCount`와 일치), 중복 0, 누락 0
- 136개는 문자열까지 동일
- 4개만 표기 차이였고, 남은 미매칭 4개와 **1:1로 대응**(추정 아님 — 일대일이라 다른 해석이 없다):

| 대륙 | 노션 표기 | 거래소 실제 표기 |
|---|---|---|
| 아르테미스 | 루페온 **시**상 조각 | 루페온 **신**상 조각 |
| 유디아 | 태양 소금 | 태양소금 |
| 유디아 | 사피라 연구 일지 | 사피라 연구일지 |
| 로헨델 | 엘조**원**의 나뭇가지 | 엘조**윈**의 나뭇가지 |

매칭 키가 아이템 이름이므로 **거래소 표기를 정본**으로 코드에 넣는다(사용자 확인 완료).

## 설계

### 왜 백엔드를 건드려야 하나

한 대륙의 7개가 **14페이지에 흩어져** 있다. 현재 `/api/market/adventure`는 페이지 단위 패스스루라
"루테란 서부 7개"를 만들 방법이 없다. 이름으로 7번 검색하는 건 API 7회 + 부분일치 오염이라 더 나쁘다.

→ **전량 수집 후 캐시**. 14페이지를 한 번 긁어 Redis에 통째로 넣고(TTL 10분) 전량을 서빙한다.

부수 효과가 오히려 좋다: 지금은 페이지를 넘길 때마다 API 1회인데, 바뀌면 **10분에 14회로 상한이
고정**된다. 페이징도 사라진다(대륙당 7개).

대가는 캐시 미스 시 토큰 14개를 한 번에 쓰는 것. 이 버킷은 수집기와 공유하므로(D-03) 중간에 토큰이
떨어지면 **검색이 실패하고 물러난다** — Core Value(수집)가 온디맨드 검색보다 우선이라는 기존 규율
그대로다(`MarketSearchService` 주석).

### 왜 대륙 매핑은 프론트에 두나

`categories.ts`(대시보드 물품 분류)·`classes.ts`(직업군)와 같은 성격이다: **API가 주지 않는 정적
도메인 분류표**이고, 그것을 읽는 유일한 소비자가 그 화면이다. 백엔드에 두면 서버가 화면 분류를
알아야 하고 매핑이 바뀔 때마다 배포가 필요하다. 서버는 "140개를 준다"까지만 안다.

## 작업

### 1. 백엔드 — 전량 수집 + 캐시

`MarketSearchService.getAdventureAll()` 신설:
- Redis `market:adventure:all`, TTL 10분. 히트면 API 0회.
- 미스면 page 1부터 `client.searchMarket("100000", null, null, page, "CURRENT_MIN_PRICE", "ASC")`를
  누적 개수가 `totalCount`에 도달할 때까지. **페이지 상한(안전장치)**을 둬서 응답이 이상해도
  무한 루프가 되지 않게 한다.
- 페이지마다 `rateLimiter.tryAcquire()`. 실패 시 `RateLimitedApiException`.

`MarketController.adventure()`가 이 메서드를 쓰도록 교체. `q`/`sort`/`dir`/`page` 파라미터는 제거
(필터·정렬은 프론트가 140개 위에서 한다). `search()`는 **손대지 않는다** — 아바타가 쓴다.

기존 `MarketControllerIT`의 adventure 테스트 4건은 새 계약(전량 반환·파라미터 없음)에 맞게 수정.

### 2. 프론트 — `features/market/tomes.ts` 신설

- `CONTINENTS`: 20대륙 × 7아이템 이름(거래소 표기), 게임 진행 순서.
- `groupByContinent(items)`: 서버가 준 140개를 대륙 leaf로 묶는다. **서버 응답이 단일 출처** —
  표에 있으나 거래소에 없는 이름은 그리지 않고, **거래소에 새로 등장했는데 표에 없는 아이템은
  버리지 않고 `미분류` leaf로** 노출한다(신규 대륙 추가 시 조용히 사라지는 게 최악).
- `전체` leaf를 맨 위에 두고 기본 선택(사용자 결정) — 아이템 이름만 알고 어느 대륙인지 모를 때
  여기서 찾는다.

### 3. 프론트 — `AdventurePage` 재구성

- 좌측 카드: `대륙` 그룹 헤더 + lucide 지도 아이콘 + 하위 leaf(전체 + 20대륙, 각 개수 표시).
  대시보드 `CategoryNav`의 두 얼굴(lg 세로 목록 / 모바일 가로 칩) 규율을 따른다.
- 중앙: 선택 범위의 아이템 목록(`MarketResultList`) + 검색바 + 정렬.
- **검색·정렬·필터 전부 클라이언트에서** 140개 위에 적용. 검색은 현재 선택된 범위 안에서만 거른다.
- 페이지네이션 제거(전체 140, 대륙당 7).
- 정렬 시 가격 `null`(즉시구매 매물 없음)은 **항상 뒤로** — 0으로 취급하면 "제일 싼 물건"으로
  올라와 거짓말이 된다(`MarketResultList`가 값을 지어내지 않는 규율과 같은 이유).

## 검증

- `./gradlew build` 통과(기존 IT 포함, adventure 테스트는 새 계약으로 수정).
- `npm run build` 통과.
- **대조 스크립트 재실행**: `tomes.ts`의 140개 == 라이브 거래소 140개(집합 동일, `미분류` 0).
- 라이브: 대륙 전환 시 7개가 뜨고, `전체`에서 검색이 동작.
