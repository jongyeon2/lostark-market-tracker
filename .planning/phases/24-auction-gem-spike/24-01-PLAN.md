# Phase 24-01 — 경매장 보석 카탈로그 스파이크 (GEM-01)

## 왜 스파이크부터인가

이 프로젝트는 **경매장(AUCTIONS) API를 한 번도 호출한 적이 없다.** 코드 전체에 `auctions` 문자열이 0건이고
(`LostarkSpikeClient`·`LostarkApiClient`·`LostarkNewsClient` 전부 `/markets/*`·`/news/*`만), 거래소와
요청 shape·응답 구조·식별자 체계가 다르다.

착수 게이트는 프로젝트 헌법이다 — CLAUDE.md: *"Task 0(API 검증 스파이크) 전엔 데이터 모델 미확정"*.
Phase 12(각인서·융화재료 카테고리), Phase 21(재련재료 카탈로그)이 같은 순서를 지켰고, **Phase 21에서
실제로 가정이 깨졌다**: "아크그리드젬 = 경매장"이라고 믿고 설계 스펙에 적어뒀는데 실측해보니 거래소
(230000)였다. 그 발견 덕에 이 phase의 스코프가 "보석+아크그리드젬"에서 **"보석만"** 으로 줄었다.

설계 스펙(`2026-07-14-v1.5-market-scope-ux-design.md` line 135)이 남긴 미해결 질문이 이 스파이크의 핵심이다:

> 경매장 보석의 "현재가" 표현: BuyPrice(즉시구매) 최저 vs BidStartPrice — Stage 2 스파이크.

경매장은 **입찰(auction)** 이라 거래소의 `CurrentMinPrice`처럼 "현재가"가 자명하지 않다. 즉시구매가가
없는 매물이 있을 수 있고, 입찰가는 시간에 따라 오른다. **무엇을 "현재가"라 부를지 모르는 채로 화면
계약(UI-SPEC)이나 DTO를 먼저 쓰는 건 순서가 거꾸로다.**

## 스코프 (사용자 확정 2026-07-15)

**티어4 보석 8·9·10레벨만**, 클래스 무관. 아크그리드젬 제외(이미 거래소로 Phase 22 편입).
이 phase는 **findings 산출까지** — 조회 API·캐시·화면은 GEM-02로 분리(findings 확정 후 계획).

> 빗나간 가설은 "가설 X → 실측 Y"로 남긴다(Phase 21이 아크그리드젬으로 한 그대로).

|---|---|---|
| H1 | 경매장은 기존 MARKETS와 **같은 JWT 키**로 인증된다 | 같은 `LOSTARK_API_KEY`로 200이 오는지 |
| H2 | 레이트리밋 버킷이 **거래소와 공유**된다(키당 100/min) | 경매장 호출 직후 `x-ratelimit-remaining`이 거래소 호출과 **연속 감소**하는지 |

## Core Value 가드

수집(`PriceCollector`)·캐시(`cache/`)·`price_snapshot`·event-impact **0줄**. 스파이크 코드는
`@Profile("spike")` + `@Disabled` 이중 격리라 일반 실행·CI 어디에도 개입하지 않는다.
DB 스키마 무변경(마이그레이션 0), 프로덕트 UI 0줄.

**보석은 시계열로 기록하지 않는다** — 이 phase는 아무것도 적재하지 않고, GEM-02도 "현재가 둘러보기"
(온디맨드+캐시)로 한정한다. 거래소 10분 수집이 Core Value이고, 경매장은 그 위에 얹는 곁가지다.
