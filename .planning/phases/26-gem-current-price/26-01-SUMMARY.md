# Phase 26-01 SUMMARY — 보석 현재가 둘러보기 `/gems` (GEM-02)

## 무엇을 했나

Phase 24가 잠근 티어4 보석 6종(겁화·작열 × 8/9/10)의 **최저 즉시구매가**를 백엔드가 온디맨드로
조회·캐시해 `GET /api/gems`로 서빙하고, 신규 `/gems` 페이지에 표시한다. 상단내비 4번째 항목.

- **`gem/` 독립 패키지** — `LostarkAuctionClient`(경매장 전용, 거래소 클라이언트 재사용 안 함)
  · `GemCatalog`(6종 상수, DB 아님) · `GemService`(캐시-어사이드) · `GemDtos`
- **`GemController`** — `GET /api/gems` 공개 read
- **`GemPage`** — Card + 자체 AsyncBoundary + 계열 그룹 2개 × 3행
- 기존 화면(대시보드·`CategoryNav`·`ItemCard`·`NewsPanel`) **0줄**. `TopNav`·`main.tsx` 각 1줄.

## 🔑 라이브가 잡아낸 것 — 공유 토큰 버킷 누락

**첫 라이브 실행에서 겁화 3 OK / 작열 3 × HTTP 429가 났다.**

원인은 내 설계 실수였다. 이 프로젝트엔 이미 `RedisTokenBucket`(단일 전역 버킷, 주석에 **"one API key,
one bucket" D-03**)이 있고 수집기·백필 러너가 호출 전 `tryAcquire`로 토큰을 얻는데, **보석만 그걸
우회**했다. Phase 24 스파이크로 "경매장이 거래소와 서버 쿼터를 공유한다"를 측정해놓고, 정작 코드에선
같은 버킷을 안 쓴 것 — 앱의 회계는 "수집기만 쓴다"고 믿는데 보석이 몰래 써서 실제 한도를 넘겼다.

**수정:** `GemService.fetchOne`이 같은 버킷에서 토큰을 얻고, 못 얻으면 **호출 없이** `RATE_LIMITED`.
수정 후 라이브 재검증에서 **6/6 OK · 429 0건**.

## 결정

**온디맨드 캐시(폴러 없음).** 뉴스(17.2)는 6h 폴러지만 보석은 다르다: 뉴스는 대시보드 방문자 전원이
보고, 보석은 전용 페이지다. 5분 폴러는 **아무도 안 보는 시간에도 분당 1.2콜을 수집 예산에서 영구히
빼간다**. 캐시-어사이드는 무방문 시 **0콜**.

**그래서 "5분마다 갱신"이라고 쓰지 않는다.** 승인 목업의 부제가 그랬지만 온디맨드 캐시에선 **거짓**이다
— 주기 갱신이 아니라 "누가 볼 때, 최대 5분 지난 값"이다. `기준 시각 {formatKst}`으로 대체했다.
문구를 참으로 만들려고 동작을 바꾸는 건 본말전도다.

**`RATE_LIMITED`를 `FETCH_FAILED`와 분리.** "고장"과 "수집(Core Value)에 예산을 양보함"은 사용자에게
다른 사실이다 → "불러오지 못함" vs **"잠시 후 다시"**. 서버 측 429도 같은 의미라 같은 상태로 매핑.

**레이트리밋 스냅샷은 캐시하지 않는다.** `OK`/`NO_BUYOUT`/`FETCH_FAILED`는 경매장이 준 **답**이라
캐시가 맞다(재조회는 예산 재소모). `RATE_LIMITED`는 **묻지도 않은 것** — 5분 굳히면 토큰이 몇 초 뒤
회복돼도 열화가 지속되고, 재시도 비용은 0이다(토큰 없으면 네트워크에 안 나감).

**행이 링크가 아니다.** 보석은 `Id`도 시계열도 없어 갈 곳이 없다. `ItemCard`처럼 생겼는데 안 눌리는
가짜 어포던스를 만들지 않는다 — 별도 페이지를 택한 이유이자, `/gems`가 대시보드에 안 들어간 이유.

**`ItemIcon` 재사용 거부.** 그 컴포넌트의 폴백 글리프가 `roleGroup`에 묶여 있는데 보석엔 없다. 끼우려면
공용 컴포넌트에 보석 분기를 더해 **기존 3화면을 오염**시켜야 한다. `GemIcon`이 고정 슬롯에 직접 렌더.

## 편차

1. **공유 토큰 버킷 누락 → 429** (위 참조, 수정 완료)
2. **`RATE_LIMITED` 상태 신설** (계획엔 3값이었음)
3. **가격 행 라벨 제거** — 라이브 렌더에서 `최저 즉시구매가`가 6행 반복돼 정작 비교할 숫자를 가렸다.
   부제가 이미 말하므로 중복(레벨 행에서 계열을 뺀 것과 같은 원칙). 🪙 + 골드만.
4. **`AsyncBoundary.pendingFallback`은 없다** — UI-SPEC 초안의 6행 Skeleton은 공용 컴포넌트 수정을
   요구하는데 같은 문서가 "0줄 수정"을 약속했다 → `NewsPanel` 관례대로 기본 `LoadingState`.
5. **`status=OK` + `minBuyPrice=null`** (계약 위반) 방어 추가 — tsc가 잡았다. 빈 칸/크래시 대신 없다고 말한다.

## 보고 사항 (고치지 않음 — 스코프 밖)

**공유 리미터는 서버 한도를 넘길 수 있다.** 버킷이 **용량 90 + 리필 90/분**이라 가득 찬 상태에서
1분간 최대 **180콜**이 가능한데 서버 한도는 **100/분**이다. 즉 리미터를 성실히 지켜도 429가 날 수 있고,
dev 기동 시엔 수집 49 + 백필 49가 동시에 터져 더 쉽게 넘는다. **Phase 2부터 있던 성질**이며 수집기는
`Retry-After` 재시도로 흡수한다. 고치려면 Core Value 코드(`RateLimiterConfig`/`RedisTokenBucket`)를
수정해야 하므로 **GEM-02의 "수집 0줄" 가드를 지켜 손대지 않았다.** 별도 판단 필요.

## Core Value 가드

수집(`PriceCollector`)·가격 캐시·event-impact·`price_snapshot`·`ratelimit/`·마이그레이션 **0줄**
(`git status`로 확인). 보석은 독립 패키지·독립 Redis 키(`gem:latest`)·독립 read-path,
**시계열 미기록**(DB에 한 줄도 안 씀). 경매장 호출은 캐시 미스에만 6콜, 무방문 시 0콜, 그리고 이제
수집기와 **같은 버킷**에서 예산을 나눠 쓴다.
