## 🔑 계획대로 안 된 것 — 유효성 검사가 정상 덤프를 거부했다

`pg_restore -l /dev/stdin`으로 덤프를 검증하려 했는데 **정상 덤프까지 거부**됐다. 커스텀 포맷은
seek이 필요한데 **파이프는 seek이 안 된다**. 그대로 뒀으면 **모든 백업이 매일 실패**했을 것이다.

→ 컨테이너 안에 실파일로 쓴 뒤 검사하도록 수정. 4가지 입력으로 실증:

| 입력 | 결과 |
|---|---|
| 정상 덤프 | ✅ 통과 |
| 잘린 덤프(500바이트) | ✅ 거부 |
| 0바이트 | ✅ 거부 |
| 랜덤 쓰레기 | ✅ 거부 |

**이게 계획을 코드로 옮기기만 하고 안 돌려봤으면 못 잡았을 버그다.**

## 검증 — 실데이터로 복원까지 실제 수행

dev의 `lostark-postgres`(postgres:16, 실스키마·실데이터)로:

**① 복원 대조** — 덤프(129,760 bytes) → 일회용 PG16 컨테이너 `pg_restore` → **8개 테이블
`COUNT(*)` 전부 일치**:

`price_snapshot` 6914 · `item_daily_stats` 1084 · `collection_run` 276 · `tracked_item` 53 ·
`gem_price_snapshot` 18 · `flyway_schema_history` 9 · `coupon` 2 · `game_event` 1

> ⚠️ `n_live_tup`(추정치)는 `price_snapshot`을 **9109**로 보고했다 — 실제 6914와 **2195 차이**.
> 추정치로 대조했으면 거짓 불일치가 났다. 런북에도 `COUNT(*)`를 쓰라고 명시했다.

**② 스크립트 전체 실행** — 목 PAR/ping 서버(스크래치패드)를 세워 **덤프→검사→업로드→ping** 전 구간
통과. 서버 수신 확인: `db/2026-07-16.dump`, 129,760 bytes, magic `PGDMP`.

**③ 🔑 실패 경로 — 실패를 성공으로 보고하지 않는가** (데드맨 스위치의 전제)

PAR 만료를 404로 재현 → `ERROR: 업로드 실패 (HTTP 404) — PAR 만료 여부 확인` · **종료 코드 1** ·
**PUT 0건 · ping 0건**. 즉 실패한 실행은 신호를 남기지 않는다 → 침묵이 곧 알림이 된다.

**④ PAR URL 유출 없음** — 전 실행 로그에 URL 미출현. `die` 메시지는 **변수명만** 말한다.

**⑤ shellcheck 통과** (지적사항 0). `SC2016` 1건은 **의도**라 사유 주석과 함께 억제 —
`$?`/`$rc`는 컨테이너 안 셸이 확장해야 한다.

## ⚠️ 검증하지 못한 것 (정직히)

- **실제 오라클 오브젝트 스토리지 업로드** — PAR이 없어 목 서버로만 확인. HTTP 계약(PUT→200)은
  같지만 OCI 실응답·객체 생성은 미확인.
- **실제 healthchecks.io ping** — 목으로만.
- **cron 등록·VM 실행** — 사용자 설정 후 첫 실행에서 확인 필요.

## 판단

- **PG만 백업.** Redis=캐시, Caddy 인증서=재발급. 되돌릴 수 없는 건 PG뿐이다.
- **DB 전체 덤프.** `tracked_item`은 시더가 재생성하지만, 골라 뜨면 테이블이 늘 때마다 스크립트를
  고쳐야 하고 빠뜨리면 조용히 소실된다. 전체도 130KB다.
- **삭제 로직 없음.** 보관은 서버측 수명주기가 한다 — VM은 지울 권한 자체가 없다.
- **ping 실패는 스크립트를 실패시키지 않는다.** 백업은 이미 끝났다. 오탐 알림이 뜰 뿐이고,
  **거짓 경보가 거짓 침묵보다 낫다.**
- **런북에 "PAR로 다운로드 불가"를 명시.** 쓰기 전용을 고른 대가라, 복원하는 날 당황하지 않도록
  콘솔 경로를 적었다.
