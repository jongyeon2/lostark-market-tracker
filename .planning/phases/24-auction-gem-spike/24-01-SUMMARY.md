# Phase 24-01 SUMMARY — 경매장 보석 카탈로그 스파이크 (GEM-01)

## 무엇을 했나

경매장(AUCTIONS) API를 **처음으로 실호출**해 GEM-02가 추측 없이 계획 가능한 상태를 만들었다.
산출물: `24-SPIKE-FINDINGS.md`(H1~H7 실측 + 카탈로그 잠금 + "현재가" 정의 + exit-gate).

- `LostarkSpikeClient` — `getAuctionOptions()`·`searchAuctionItems(...)` 추가. **거래소용
  `searchMarketItems`를 재사용하지 않았다**(엔드포인트·body·응답 shape가 전부 다름). 키 정규화·
  `authorization` 헤더는 기존 것 그대로 재사용 — 새 키·새 설정 0.
- `AuctionsApiSpikeTest`(신규, `@Disabled`+`spike` 프로파일) — 4 케이스: 옵션/버킷 1차, 티어4 카탈로그,
  **통제 버킷 프로브**, 8~10레벨 정조준. 응답 **원문**을 UTF-8 파일로 기록.

## 스파이크가 실제로 잡아낸 것 (가정이었다면 틀렸을 것들)

1. **레이트리밋 버킷을 거래소와 공유** — 보석 조회가 10분 수집 예산을 직접 깎는다. GEM-02에서
   **캐시가 필수**임이 추정이 아니라 측정으로 확정됐다(Core Value 가드).
2. **응답에 `Id`가 없다** — 거래소 `Id`(=`external_item_id`, 워치리스트 PK)에 대응하는 필드 부재.
   워치리스트 모델을 재사용하려 했다면 설계 단계에서 막혔을 것.
3. **`Level`은 보석 레벨이 아니다** — 전 보석 `Level:1640`(착용 아이템 레벨). 보석 레벨은 **이름 안**에만
   있고 숫자 레벨 필터가 없다. "8~10레벨만"이라는 스코프를 `Level` 필드로 구현했다면 조용히 오작동했다.
4. **`멸화`/`홍염` 티어4 = 0건** — 티어3라 스코프 밖(가설 반증).
5. **`Sort=BUY_PRICE` DESC는 null을 앞에 놓는다** — DESC로 최고가를 구하면 틀린다. ASC만 쓴다.

## 결정 — "현재가" = `min(BuyPrice)` (즉시구매 최저가)

설계 스펙 line 135가 남긴 미해결 질문(BuyPrice vs BidStartPrice)을 실측으로 닫았다. 후보 4개 중
**`BuyPrice`만 정답**인 이유가 데이터에 있다:

- `StartPrice`에 **1골드·22골드 매물이 실재**한다(1골드 시작 입찰 미끼) → 이걸 현재가로 쓰면
  "9레벨 겁화의 보석 = 1골드"로 표시된다.
- `BidPrice`는 입찰 0건이면 `0`(대부분) → "0골드".
- `BidStartPrice`는 **다음** 입찰 최소가 — 지금 지불하는 값이 아니다.
- `BuyPrice`만이 "지금 이거 사려면 얼마?"에 답하고, **거래소 `CurrentMinPrice`(최저 호가)와 의미가
  대응**한다 → 화면에서 같은 '최저가' 어휘를 써도 정직하다(혼합이 아니라 대응).

**`BuyPrice`는 null일 수 있다**(입찰 전용 매물). ASC 정렬이 null을 뒤로 보내므로 page1 첫 항목이 항상
실제 최저 즉시구매가다. 전 매물이 null이면 **현재가 없음**으로 정직 표기 — 값을 지어내지 않는다
(`insufficient_data`·쿠폰 `startsAt` null과 같은 원칙).

## 카탈로그 — 티어4 보석 6종 (사용자 스코프와 일치)

겁화(딜러) 8/9/10 + 작열(서포터) 8/9/10. 아이콘 전부 distinct(각인서와 달리 라벨 병기 불요),
등급은 레벨 파생(8·9=유물, 10=고대).

**전수 증명:** 겁화 1083 + 작열 1136 = **2219** = 무필터 티어4 `TotalCount` → 다른 계열 없음.

## 편차

- **레이트리밋 판정을 1회 철회했다.** 1차 측정에서 내 호출 1건 사이에 remaining이 85→53(32 감소)으로
  움직였다 — 같은 키를 쓰는 운영 수집기의 간섭. 노이즈에서 결론을 읽는 대신 **통제 측정을 추가**해
  다시 쟀다(연속 4콜 + 간섭 체크). 계획에 없던 4번째 테스트(`probeRateLimitBucketTightly`)가 그것이다.
- 간섭은 통제 측정에서도 남아 있어(a1→a2 -5) 카운터가 정밀하지 않다. 그래서 **보수적으로 "공유"로
  확정**했다 — 분리인데 공유로 가정하면 캐시가 과할 뿐이고, 공유인데 분리로 가정하면 수집기를 굶긴다.
- 실행 중 `. ./.env` 소싱이 실패하며 **키 일부가 콘솔에 출력됐다**(`.env`의 키 값에 공백이 포함돼 bash가
  뒷부분을 명령으로 해석). 산출물엔 미기재(검증됨). 아래 후속 조치 참조.
