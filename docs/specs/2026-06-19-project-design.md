## Problem Statement

신입 백엔드 개발자 취업 준비생이, 포트폴리오에서 **설명 가능한 백엔드 엔지니어링 실력**을 증명할 프로젝트가 필요하다. "외부 API를 호출해 JSON을 보여주는" 토이 프로젝트가 아니라, 외부 제약(레이트리밋, JWT 인증) 아래서 데이터를 안정적으로 수집·저장·서빙하는 시스템을 만드는 것이 목표.

선택한 도메인은 로스트아크 거래소(MARKETS) 시세. 본인이 로아 유저이고, 특히 강화 수단인 **융화재료**처럼 골드가 많이 드는 고변동 품목의 시세를 자주 확인한다. 공식 API는 과거 시세를 충분히 제공하지 않으므로, **시세 이력을 직접 구축하는 것 자체가 이 백엔드가 존재하는 이유**가 된다.

엔지니어링 정체성: "레이트리밋이 걸린 외부 마켓 API에서 시세를 주기 수집해 시계열로 적재하고, Redis 캐시 계층으로 서빙하며, 주요 게임 이벤트와 가격 변동을 시점 상관시키는 데이터 파이프라인." 도메인이 게임일 뿐, 구조는 금융 마켓 데이터 파이프라인과 동일하다.

## What Makes This Cool

단순 시세 조회가 아니라, **"언제 가격이 올랐는가"에 더해 "왜 올랐을 가능성이 있는가"**에 답하는 트래커다.

10분 단위로 수집한 가격 시계열 위에, 관리자가 등록한 주요 게임 이벤트(로아온, 대형 업데이트, 시즌 종료, 밸런스 패치)를 겹친다. "시즌 종료 D-3에 아비도스 융화재료가 X% 올랐다" 같은 서사를, 추측이 아니라 본인이 수집한 데이터로 보여준다. 도메인 지식(어떤 품목이 왜 변동이 심한지)이 데이터로 증명되는 지점이 이 프로젝트의 차별점이다.

## Constraints

- **기간:** 약 1개월.
- **기술 스택:** Java / Spring Boot / JPA / Redis. (MSA·Kafka·Spring Batch는 명시적으로 제외 — 한 달, 단일 인스턴스, 첫 스케줄러/캐시 학습에 과한 고도)
- **개발자 경험:** Spring Boot + JPA 자주 사용(CRUD 능숙). 스케줄러·캐시·레이트리밋은 처음 → 학습 곡선이 곧 포트폴리오 차별점과 일치.
- **API 접근:** 로스트아크 개발자 포털 키(JWT) 보유, 재발급 가능. `Authorization: bearer {token}`. 레이트리밋 키당 분당 100회(정확 수치 확인 필요).
- **데이터 소스:** 거래소(MARKETS)만. 경매장(AUCTIONS)/보석은 v2.

## Premises (Phase 3, 전부 동의됨)

1. **API를 코드보다 먼저 검증한다.** 코드 작성 전, 발급 키로 `markets/items`에 실제 융화재료 품목을 호출해 응답 필드(현재 최저가/평균가/거래량/일별 stats)와 요청 포맷을 직접 확인한다. 최대 리스크.
2. **레이트리밋은 선제 설계하되 MVP 규모에선 한계에 안 부딪힌다.** 거래소 검색은 요청 1건에 여러 품목을 페이지로 반환하므로 20~30품목이면 분당 100회에 한참 못 미친다. 그래도 토큰버킷/요청 분산/429 처리를 제대로 구현한다. "지금 필요해서"가 아니라 "올바른 패턴이고 확장 대비이며 핵심 showcase라서". 면접에서도 이렇게 솔직히 설명한다.
3. **Redis 역할을 정직하게 정의한다.** (a) 품목별 최신가 핫 리드 경로 캐시-어사이드, (b) 스케줄러 토큰버킷/락. MVP 규모면 DB만으로 읽기 감당 가능함을 인정. "다들 쓰니까"가 아니라 패턴 증명 + 확장 시 옳은 선택이라 쓴다.
4. **저장은 원본 보관, 롤업은 stretch.** 10분 스냅샷을 원본 그대로 보관(월 수십만 행, 부담 없음). 일 단위 롤업은 성능 최적화 stretch.
5. **상관은 인과가 아니다.** 이벤트-가격은 "시점상 겹친다(상관)"이지 "이벤트가 가격을 올렸다(인과)"가 아니다. 응답 문구/UI를 거기에 맞추고 과대 주장하지 않는다.
6. **스코프 동결.** 위가 MVP 전부. 자동 뉴스 파싱·이벤트 자동 추출·알림·경매장 보석·캐릭터 분석은 전부 v2.

## Approaches Considered (Phase 4)

### Approach A: 직선형 모놀리스 — B로 가는 1단계 워킹 스켈레톤 (경쟁안이 아님)
고전적 레이어(controller → service → repository). `@Scheduled`가 워치리스트를 동기 순회하며 API 호출, **레이트리밋 없이 일단 적재**(MVP 규모에선 한계 미달), JPA 저장. 캐시는 Spring `@Cacheable` + RedisCacheManager로 최소. 난이도 S~M, 리스크 낮음. 이것은 버려지는 대안이 아니라 **B의 1주차 골격**이다(레이트리밋·캐시·비동기는 그 위에 올림). 별도 인메모리 레이트리밋(Resilience4j 등)은 만들지 않음 — Redis 토큰버킷이 유일한 리미터라 throwaway 방지.

### Approach B: 수집/처리 분리 + Redis 레이트리밋 (이상적 구조) — 채택
단일 앱이되 깔끔히 분리. 스케줄러가 수집 태스크를 `@Async` 바운드 스레드풀에 위임해 API 지연이 틱을 막지 않게 함. 레이트리밋은 **Redis 기반 토큰버킷**(재시작·다중 인스턴스에도 정확). 핫 리드 경로는 **RedisTemplate로 직접 캐시-어사이드**. 시계열은 `(tracked_item_id, collected_at)` 복합 인덱스로 범위 쿼리 최적화. 난이도 M~L, 리스크 중(새 개념 다수). 본인이 배우려는 것에 학습이 정확히 꽂히는 유일한 안.

### Approach C: 이벤트 상관을 1급 시민으로 (변형안)
아키텍처 중심을 파이프라인이 아니라 차별화 기능(이벤트 상관)에 둠. 각 이벤트의 ±N시간 윈도우 가격 델타를 계산하는 집계 잡을 핵심 도메인으로. 가장 차별화되지만, 파이프라인이 단단해지기 전 분석에 과투자할 위험(도금)과 윈도우 델타 엣지케이스(희소 데이터·경계 이벤트)가 리스크.

## Recommended Approach

**B를 목표로 하되 A→B 순서로 빌드하고, C의 이벤트 임팩트를 그 위 헤드라인 기능으로 올린다.**

근거: 목표가 "백엔드 엔지니어링 실력 증명"이고, 학습이 필요한 부분(스케줄러·캐시·레이트리밋)이 곧 포트폴리오 차별점인데, B가 그 셋을 정면으로 깊게 다루는 유일한 안이다. JPA가 이미 익숙해 CRUD 배관은 빠르게 끝나므로 한 달이면 충분. A는 안전하지만 본인을 저평가하게 만들고, C는 매력적이지만 단독으로는 순서가 위험하다. A를 워킹 스켈레톤으로 먼저 세워 B의 심화를 단계적으로 올리면 B의 리스크가 완화된다.

### 데이터 모델 (초안, 스파이크 후 확정)
- **모든 타임스탬프는 UTC로 저장**(Postgres `timestamptz`), 윈도우/조인 계산도 UTC, KST는 응답/표시 단계에서만 변환. (로아는 KST 기준 게임이라 이벤트-가격 상관에서 9시간 오프바이 버그 방지)
- **tracked_item** (품목 카탈로그/워치리스트): id, 로아 품목 식별자, name, category, active, created_at
- **price_snapshot** (시계열): id, tracked_item_id(FK), collected_at(UTC), min_price(현재 최저가), avg_price(평균가), trade_count(거래량). **복합 인덱스 (tracked_item_id, collected_at)**. (MVP는 단일 소스라 `source` 컬럼은 두지 않음 — 경매장 추가하는 v2에서 도입)
- **game_event**: id, event_type(LOA_ON / MAJOR_UPDATE / SEASON_END / BALANCE_PATCH), title, occurred_at(UTC, **MVP는 단일 시점**), description. (로아온 같은 기간형 이벤트의 start/end 모델은 v2 — 단일 시점이어야 ±N시간 윈도우 계산이 정의됨. created_by는 인증 모델이 없으므로 생략)

### 핵심 컴포넌트 (B)
- **LostarkApiClient** — RestClient/WebClient, JWT bearer, `markets/items` POST 검색. 429(레이트)와 401(인증/토큰 만료)을 **구분 처리**, 5xx는 백오프. (포털 키는 발급 시 장기 유효라 가정하되, 401이 지속되면 키 재발급 신호로 로깅)
- **Rate limiter** — Redis 토큰버킷. 손으로 짜면 경쟁 조건/재시작 정확성 함정이 큼 → **`(tokens, lastRefillTs)`를 저장하고 acquire 시 Lua로 원자적 lazy refill**(별도 리필 스레드 금지 → 재시작에도 정확). 학습 비용을 줄이려면 **Bucket4j + Redis 백엔드** 채택. 어느 쪽이든 2~3일 예산.
- **PriceCollector** — `@Scheduled(fixedDelay)`(10분) 트리거. **재진입 방지:** 이전 수집이 도는 중이면 틱 스킵(Redis `SETNX`+TTL 잡 락 / 단일 플라이트). 수집 단위는 카테고리 배치 우선(검색 1건이 여러 품목 반환, 전제 2와 일치). 카테고리/품목 태스크를 `@Async` **고정 풀(size 4, caller-runs)**에 위임 → API 지연이 틱을 막지 않음. 실제 배치 단위·풀 크기는 Task 0으로 확정.
  - **JPA×@Async 함정:** 영속성 컨텍스트는 `@Async` 스레드로 전파 안 됨 → 비동기 태스크 안에서 **새 트랜잭션을 열고 엔티티가 아니라 ID를 넘긴다**(LazyInitialization 회피).
  - **부분 실패:** 품목 수집이 실패하면 그 틱은 **스냅샷을 쓰지 않고**(널 행 금지) 성공/실패만 기록. 시계열에 구멍이 생길 수 있음을 event-impact가 인지(아래).
- **Persistence** — Spring Data JPA 리포지토리. 스냅샷 적재, 범위 조회.
- **Cache-aside** — 품목별 최신가를 RedisTemplate로 캐싱. **수집기가 스냅샷을 쓸 때마다 최신가 키를 갱신/무효화**(또는 TTL ≤ 수집주기) → DB엔 더 최신값이 있는데 캐시가 stale을 주는 상황 방지. 읽기는 캐시 미스 시 DB 조회 후 채움.

### REST API (초안)
- `GET /api/items` — 워치리스트 조회
- `GET /api/items/{id}/latest` — 캐시된 최신가
- `GET /api/items/{id}/prices?from=&to=` — **타임라인: 기간 스냅샷 + 겹치는 이벤트 함께 반환** (핵심 기능)
- `GET /api/items/{id}/event-impact?window=Nh` — 이벤트별 ±N시간 윈도우 가격 델타(상관, C). **v1 지표 고정:** `(이벤트~이벤트+Nh 첫 스냅샷 min_price) / (이벤트-Nh~이벤트 마지막 스냅샷 min_price) − 1`. 윈도우 내 스냅샷이 임계치 미만으로 희소하면 계산하지 않고 `insufficient_data` 응답(전제 5의 상관≠인과와 일관).
- `GET /api/health/collection` — 마지막 수집 시각·성공/실패 카운트. 무인 파이프라인 가동 여부를 리뷰어가 즉시 확인 → 운영 성숙도 showcase.
- 관리자: `POST/PUT/DELETE /api/admin/events`, `POST/DELETE /api/admin/items`. **MVP는 단일 공유 시크릿/Basic auth 또는 로컬 전용 비보호로 명시**(유저 모델 없음).

## Open Questions

- **API 응답 실측:** `markets/items`가 실제로 현재 최저가/평균가/거래량/일별 stats를 어떤 필드·구조로 주는가? 요청 본문(카테고리/검색어/페이징) 형태는? → 스파이크로 즉시 해소(아래 Task 0).
- **레이트리밋 정확 수치/헤더:** 분당 100회가 맞는지, `X-RateLimit-*` 류 잔여 헤더를 주는지(주면 토큰버킷을 헤더 기반으로 보정 가능).
- **품목 식별 안정성:** 융화재료 등 품목을 이름으로 잡을지, 품목ID로 잡을지(시즌/패치로 신규 품목 추가 시 워치리스트 갱신 방식).
- ~~이벤트 시간 모델~~ **(해결):** MVP는 단일 `occurred_at`(UTC). ±N시간 윈도우 계산이 단일 시점을 전제하므로 고정. 기간형(로아온)은 v2.
- **부분 실패/데이터 구멍 (설계에 반영됨):** 수집 실패 틱은 스냅샷을 쓰지 않으므로 시계열에 구멍이 생길 수 있음 → event-impact가 희소 윈도우를 `insufficient_data`로 처리.
- **DB 선택:** Postgres 권장(시계열 범위 쿼리/인덱싱에 무난). H2는 로컬 테스트용으로만.

## Success Criteria ("done"의 정의)

- 스케줄러가 10분 주기(`fixedDelay`)로 시세를 수집하고, 이전 실행이 도는 중이면 틱을 스킵하며, 레이트리밋을 넘지 않는다.
- **토큰버킷이 lazy timestamp refill로 동작해 재시작 후에도 토큰 수가 올바르게 복원된다**(별도 리필 스레드에 의존하지 않음). 이 항목은 해당 알고리즘을 쓸 때만 참 — 그래서 알고리즘을 명시했다.
- 품목 수집 실패 시 스냅샷을 쓰지 않고(구멍 허용) 수집 결과를 기록한다. event-impact는 희소 윈도우를 `insufficient_data`로 반환한다.
- 스냅샷이 시계열로 적재되고, 타임라인 엔드포인트가 임의 기간의 스냅샷 + 겹치는 이벤트를 함께 반환한다.
- 최신가 읽기가 Redis 캐시에서 서빙됨을 **테스트로 검증**: 리포지토리를 spy해 2번째 읽기에서 DB 호출이 0임을 단언(또는 캐시 히트 카운터 메트릭).

## MVP Scope (확정)

신뢰 가능한 **수집 파이프라인이 1순위**, event-impact는 2주차 말 게이트 통과 조건부 헤드라인.

- 거래소(MARKETS)만, 워치리스트 20~30품목, 10분 `fixedDelay` 수집.
- **틱 내 카테고리 병렬 팬아웃 + `CompletableFuture.allOf().join()`** (per-call 타임아웃 필수). `fixedDelay`가 틱을 직렬화 → **분산 락 없음**. [1A]
- Redis 토큰버킷(또는 Bucket4j) 레이트리밋 — **의도적 학습 쇼케이스**(전제 2). README에 정직히 서술. (Codex 7·8의 "과중" 지적은 학습 목표라 합의된 트레이드오프로 유지, 재오픈 안 함.)
- 최신가 Redis 캐시-어사이드 + 쓰기 시 무효화.
- `collection_run` 실행 이력 + `GET /api/health/collection`. [3A]
- 조회 API: `/api/items`, `/api/items/{id}/latest`(캐시), `/api/items/{id}/prices`(타임라인=스냅샷+겹치는 이벤트, **큰 범위 서버 다운샘플** [7A]), 관리자 이벤트/품목 CRUD(**시크릿 인증** [6A]).
- `/api/items/{id}/event-impact`(상관, v1 = 단일 품목 이벤트 전후 변화율) — **2주차 말 게이트 통과 시에만 MVP**.
- 격리된 시드/데모 데이터, README 데모 표면, CI(Testcontainers), 핵심 경로 테스트.

- **시간 필드:** UTC 저장. `collected_at` / `fetched_at` / `created_at` / `updated_at` 전부 **`TIMESTAMPTZ`**.
- **price_snapshot 제약·인덱스:** **`UNIQUE(tracked_item_id, collected_at)`** (멱등성) + 시계열 범위 조회 최적화용 **`INDEX(tracked_item_id, collected_at)`**(유니크 제약이 이 인덱스를 겸함).
- **스키마 잠금:** ✅ **Task 0 완료(2026-06-20)** — V1 4테이블 잠금. `avg_price`/`trade_count`는 **일 단위로 제공됨** 확인: `avg_price`는 V2 추가 예정(목록 `YDayAvgPrice`), `trade_count`는 per-tick 제외(상세 `Stats[]` 일 단위). 근거: TASK0-FINDINGS.md.

## Failure Modes

| 코드패스 | 실패 | 테스트 | 에러처리 | 사용자가 보는 것 | critical? |
|---|---|---|---|---|---|
| 틱 병렬 팬아웃 | 한 카테고리 hang | yes | **per-call 타임아웃 + join 타임아웃** | collection_run 부분실패 | 타임아웃 미설정 시 **CRITICAL** |
| 429 폭주 | 레이트 초과 | yes | 상한 재시도(2A)→스킵-라이트 | 구멍 + 실패 카운트 | no |
| 401 지속 | 토큰 만료 | yes | 로깅, 키 재발급 신호 | collection_run 연속 실패(health 가시) | no |
| @Async×JPA | LazyInit | yes | 새 트랜잭션 + ID 전달 | (내부) | no |
| 중복/재시도 | 같은 (품목,시각) | yes | UNIQUE 제약 → upsert/무시 | (내부, 멱등) | no |
| 캐시 stale | 무효화 누락 | yes | 쓰기 시 무효화 | (테스트로 차단) | no |
| 프로세스 다운 | 시계열 구멍 | yes(희소) | event-impact `insufficient_data` | 빈 구간 | no (HA 미구현은 수용된 한계, README 명시) |
| event-impact 오래된 앵커 | 구멍으로 stale 앵커 | yes | staleness 허용치 → `insufficient_data`(5A) | insufficient_data | no |

**유일한 critical gap:** 팬아웃 per-call/join **타임아웃 미설정** → 한 카테고리가 막히면 틱이 무한 대기. **반드시 타임아웃을 건다(T1).**

## Worktree Parallelization Strategy

| 단계 | 모듈 | 의존 |
|---|---|---|
| F. Foundation | 프로젝트 골격, 엔티티/리포(tracked_item, price_snapshot+UNIQUE, game_event, collection_run), docker-compose | Task 0 |
| A. Collection | LostarkApiClient, RateLimiter, PriceCollector(팬아웃+타임아웃), 429/401, collection_run 기록 | F |
| B. Read API | latest 캐시-어사이드, **공유 윈도우 쿼리**, timeline, 다운샘플 | F |
| C. Admin/Security | 관리자 CRUD, 시크릿 게이트 | F |
| D. Infra/Docs | CI(Testcontainers), 격리 시드, README 데모 표면 | F |
| E. event-impact | 충분성·staleness·배치 | A + B (게이트 통과 시) |

**실행 순서:** Task 0 → F(직렬, 전부 차단) → **A · B · C · D 병렬 워크트리** → 머지 → E(게이트 통과 시).
**충돌 플래그:** A와 B가 둘 다 persistence/repository를 건드림(공유 윈도우 쿼리 [4A]). B에서 공유 쿼리를 **먼저** 추출해 머지한 뒤 A가 그 위에 올리거나, 두 레인을 신중히 조율할 것.
