# Quick Task 260720-lk6 — 이벤트 영향 필터·정렬·개수 제한

## 문제 — 스크롤은 증상이고 병목은 페이로드였다

대시보드에서 물품을 고르면 **등록된 모든 이벤트**의 영향이 떴다. 사용자가 "만 건이 쌓이면 끝없이
스크롤해야 한다"고 지적했는데, 조사해 보니 그보다 앞선 문제가 있었다:

- `EventImpactItem`은 11필드(타임스탬프 3 + 제목) ≈ 250~400B → 1만 건이면 응답 **3~4MB**
- 프론트는 `EventImpactTable`과 `EventImpactCards`를 **둘 다 DOM에 넣는다**(CSS로 하나만 숨김)
  → 서브트리 **2만 개**

🔑 그래서 **클라이언트 필터는 문제의 절반만 푼다** — 3~4MB를 받아놓고 거르는 셈이다. 서버에서
자르기로 했다(사용자 결정).

## 계약 변경 — `GET /api/items/{id}/event-impact`

| 파라미터 | 기본값 | 검증 |
|---|---|---|
| `types` | 전체 | 각 값이 `EventType`, 아니면 400 |
| `sort` | `occurred_desc` | `occurred_desc`\|`occurred_asc` 화이트리스트, 아니면 400 |
| `limit` | 50 | 1..200, 아니면 400 |

응답에 **`totalCount`**(필터 적용 후·limit 적용 **전**) 추가.

## 핵심 결정 · 근거

- **`totalCount`는 `events.size()`가 아니다.** 그 구분이 없으면 잘린 화면과 전부 보여준 화면을
  구별할 수 없고, 클라이언트가 '더 보기'의 끝을 알 수 없다. 화면엔 항상 "전체 N건 중 M건"을 쓴다 —
  잘려 있다는 사실을 숨기지 않는다.
- **화이트리스트로 400을 낸다.** 모르는 `sort`를 기본값으로 흘려보내면 화면은 "오래된순"이라고
  말하는데 목록은 최신순 그대로다(`MarketSearchService`가 정렬 vocabulary에 세운 규율과 동일).
  잘못된 타입을 버리면 "그 종류엔 데이터가 없다"는 **다른 주장**으로 읽힌다.
- **`findAllByOrderByOccurredAtDesc()` 삭제.** 유일한 호출자를 바꿨는데 남겨두면 "전량 조회" 경로가
  살아있어 같은 실수를 다시 부른다. 타입 필터가 없을 땐 전체 enum을 넘겨 nullable 분기 없이 쿼리
  경로를 하나로 유지하고, `Page.getTotalElements()`가 `totalCount`를 공짜로 준다.
- **N+1 회피(D-09)는 유지될 뿐 아니라 좋아졌다.** 필터·limit을 계산 **전에** 적용하므로 `[min, max]`가
  좁아져 단일 스냅샷 범위 조회가 더 작아지고, 루프도 최대 `limit`개만 돈다.
- **"전체" 칩을 두지 않았다.** 아무것도 안 고른 상태와 전체를 고른 상태는 결과가 같고, 칩을 하나 더
  두면 "전체 + 로아ON" 같은 모순되는 조합이 생긴다.
- **칩 색·라벨은 `EVENT_MARKERS` 재사용.** 차트 마커·범례·배지가 이미 그 색이라 여기서 다른 색을
  쓰면 같은 이벤트가 화면마다 다른 색이 된다.
- **필터·정렬 변경 시 limit 리셋.** 좁아진 결과에 이전의 늘어난 limit을 들고 가면 "더 보기"를 몇 번
  눌렀는지가 화면에 남는다(거래소 검색이 검색어·정렬 변경 시 1페이지로 가는 것과 같은 이유).

## 중앙 폭

좌우 20rem→18rem, `max-w` 100rem→110rem. 1920 기준 중앙 **800 → 1024px**. 이벤트 영향 테이블이
자체 스크롤을 시작하는 지점이 뷰포트 **~1570 → ~1505px**로 내려갔다.

기본 크기로는 1920에서 21px 모자라 '일반 패치' 하나만 다음 줄로 떨어졌다. 실측(가용 862px):

앞의 둘은 창을 조금만 줄여도 다시 접히므로 글자까지 줄였다(사용자 허용). **`koLabel`은 안 줄였다** —
공유 문자열이라 타임라인 범례까지 바뀐다. ⚠️ 그래도 ~1670px 미만에서는 두 줄이 된다.

## 검증하지 못한 것 (정직하게)

dev DB에 이벤트가 **1건뿐**이라 `더 보기`와 정렬 순서 변화는 **화면에서 확인하지 못했다.** 그럴듯해
보이려고 합성 이벤트를 넣는 건 "dev는 실데이터만"이라는 기존 결정을 깨는 일이라 하지 않았고, 대신
그 동작을 IT로 고정했다(5건 · `limit=2` → `events=2`/`totalCount=5`, 잘린 2건이 최신 2건인지까지).
