<objective>
Build the two reliability primitives every collection tick depends on: (1) a **self-built Redis token bucket** (lazy refill + Lua-atomic consume) that throttles outbound calls under the API's 100/min limit and **restores its token count from Redis after an app restart**, and (2) a **productized `LostarkApiClient`** that issues the markets list call and **classifies every HTTP outcome into a distinct typed signal** — 401/403 (fatal auth), 429 (rate-limited, carrying Retry-After), 5xx/timeout (transient), other 4xx (non-retryable).

Purpose: This is the showcase learning artifact of Phase 2 (PROJECT.md "레이트리밋 = 의도적 학습 쇼케이스", D-03/D-04). The bucket is the single source of truth for throttling (Success Criterion 2 — restart restore is proven directly here, not hidden behind a library). The client's error classification is the contract the retry/partial-failure layer (02-03) and the fan-out collector (02-02) consume. Delivers COLL-03 (rate limit + restart restore) and the **classification half** of COLL-04 (the retry orchestration half lands in 02-03).

Output: `RedisTokenBucket` + `token_bucket.lua` + `RateLimiterConfig`; `LostarkApiClient` + `ApiClientConfig` + response DTOs + a 4-way exception hierarchy; a Testcontainers Redis IT proving consume/refill/restart-restore and a client test proving classification.
</objective>

## Phase Goal

**As a** collection pipeline, **I want** a rate limiter that never exceeds the API budget and survives restarts, plus an HTTP client that turns every API failure into an explicit, typed signal, **so that** the scheduled collector (02-02) and the retry/partial-failure layer (02-03) can throttle safely and react correctly to 401 vs 429 vs 5xx without crashing.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| config (env) -> app | API key (JWT secret) enters from `lostark.api.key`; must never leave via logs/exceptions |
| app -> Lostark external API | Untrusted response bodies + status codes + headers cross into the app |
| app -> Redis | Token-bucket state (counts only) crosses to a network service |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-0201-01 | Information Disclosure | API key (JWT) in logs/exceptions | mitigate | Key read from env only; normalized once in `ApiClientConfig`; never logged; typed exceptions carry status/category, never the Authorization header or key (D-08). Acceptance criterion greps for key logging. |
| T-0201-02 | Tampering | Malformed/oversized API response body | mitigate | Parse with Jackson into typed records ignoring unknown fields; per-call read timeout (~5s) caps a slow/huge response; first-party API so body-size DoS accepted. |
| T-0201-03 | Denial of Service | Redis unavailable -> limiter can't gate | mitigate | `tryAcquire` fails closed (no token granted) on Redis error so the app throttles itself rather than bypassing the limiter and flooding the 100/min API; surfaced as a skipped call to the collector. |
| T-0201-04 | Elevation/Spoofing | Counterfeit upstream (TLS) | accept | RestClient uses HTTPS baseUrl (developer-lostark...); standard JVM trust store; no custom trust-all. |
| T-0201-SC | Tampering | Dependency supply chain | accept | No new dependencies — token bucket is hand-rolled (Lua via existing spring-data-redis), client uses existing spring-web RestClient. No package-manager installs. |
</threat_model>
