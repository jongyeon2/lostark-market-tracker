<objective>
Stand up the **scheduled collection tick**: a `@Scheduled(fixedDelay)` `PriceCollector` that opens a `collection_run`, computes one **tick-normalized `collected_at`** (run-start UTC instant truncated to the minute, shared by every snapshot in the tick — D-15), **fans out one `@Async` call per active watchlist item**, awaits them all with `CompletableFuture.allOf(...).join` under a **per-call timeout AND an overall join timeout below the tick interval** (D-07 — the single CRITICAL failure mode), persists one `price_snapshot` per success **idempotently** (UNIQUE(tracked_item_id, collected_at) — D-16), and finalizes the `collection_run` with counts + a terminal status. Also seed the curated watchlist via an idempotent `ApplicationRunner` (D-01/D-02).

Purpose: This is the working end-to-end collection slice — scheduler → rate-limited client → parallel fan-out → idempotent persistence → run history. It delivers COLL-01 (10-min fixedDelay scheduler), COLL-02 (parallel fan-out + per-call timeout + fixedDelay prevents overlap), and Success Criteria 1 (collection_run rows) + 5 (UNIQUE idempotency). Retry, partial-failure status refinement, and AUTH_ERROR markers are layered on in 02-03.

Output: `CollectionConfig` (scheduling/async/executor), `WatchlistSeeder`, `ItemFetchService` (@Async) + `ItemFetchResult`, `PriceCollector`, a `PriceSnapshotRepository` existence helper, and a Testcontainers IT + a normalization unit test.
</objective>

## Phase Goal

**As a** data pipeline, **I want** a scheduled tick that polls every active watchlist item in parallel, bounded by timeouts and the rate limiter, and writes one idempotent snapshot per item plus a run-history row, **so that** price_snapshot accumulates reliably every 10 minutes without overlapping ticks, duplicate rows, or a single slow item stalling the whole tick.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scheduler (internal trigger) -> collector | Self-triggered tick; no external request, but drives outbound calls + DB writes |
| collector -> Lostark external API | Each fan-out call crosses to the rate-limited external API |
| collector -> PostgreSQL | Snapshot + run rows written from concurrent async tasks |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-0202-01 | Denial of Service | Fan-out hanging item stalls the tick forever | mitigate | Per-call timeout (~5s) + overall `allOf(...).get(timeout < tick)` (D-07 — the one CRITICAL gap); incomplete futures cancelled and counted failed. Proven by the hanging-item IT. |
| T-0202-02 | Denial of Service | Unbounded concurrency / rate-limit breach | mitigate | Bounded `ThreadPoolTaskExecutor` pool + every outbound call gated by the global RedisTokenBucket (02-01); ~10-20 item watchlist stays under 100/min. |
| T-0202-03 | Tampering | Duplicate / replayed snapshot writes | mitigate | DB UNIQUE(tracked_item_id, collected_at) + existence-check skip make re-runs idempotent (D-16); collected_at is tick-normalized so a retried tick collides intentionally. |
| T-0202-04 | Information Disclosure | API key leakage via collector logs | mitigate | Collector never logs the Authorization header/key; only categorical outcomes + counts are logged/persisted (key handling owned by 02-01 client). |
| T-0202-05 | Tampering | Stale/inactive items still polled | accept | Collector reads only active tracked_item rows; watchlist curation is small + admin-managed (Phase 4). |
| T-0202-SC | Tampering | Dependency supply chain | accept | No new dependencies — uses spring-context scheduling/async + java.util.concurrent. No package-manager installs. |
</threat_model>
