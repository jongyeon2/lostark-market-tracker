<objective>
Put the **data-quality guards** on top of the 05-01 event-impact metric (IMPACT-02): an event's `change_rate` is trustworthy **only** when there is real data tightly bracketing the event. This wave adds two locked rules to `EventImpactService` and pins them with tests:

- **Sufficiency (D-02):** `status:"ok"` requires **≥1 pre-side snapshot** in `[E−Nh, E]` **and** **≥1 post-side snapshot** in `[E, E+Nh]` (design T7 "front/back ≥1"). A side with zero in-window snapshots → `insufficient_data`, that side's anchor time `null`.
- **Staleness (D-03/D-04):** a fixed **30-minute** allowance (the 10-min cadence × 3 ticks — "tolerates ≤2 consecutive missed ticks") held as an **MVP constant**. `change_rate` is computed **only when both anchors are present AND both are fresh** (`|E − anchor| ≤ 30min`); either missing or stale → `insufficient_data` (a single stale side would distort the ratio).

The interview signal is the **two distinguishable failure modes (D-05)**: `insufficient_data` **always reports the discovered anchor times** — `null` when no snapshot existed on that side in the window (the "sparse" case, ROADMAP SC2), and the **anchor time itself** when a snapshot existed but is stale (the "stale" case, ROADMAP SC3). The caller reads *why* the number is withheld.

This **extends 05-01's service in place** (the staleness layer over the presence floor), reusing its `EventImpactItem` shape and status constants. Because 05-01's happy-path IT placed its anchors **within 30 minutes**, those tests keep passing with **zero retrofit** — this wave only adds a guard IT for the sparse / stale / boundary cases. The `@ConfigurationProperties` externalization of the threshold is explicitly **v2 (CFG-V2-01)**; MVP uses the constant.

Output: the staleness extension to `EventImpactService` and `EventImpactGuardIT`.
</objective>
